## Problem

guion is public on GitHub, but a pre-release review found that its locked dependencies carry 181 known vulnerabilities (direct: flask 2.2.5, werkzeug 2.3.7, jinja2 3.1.2, gunicorn 20.1.0, python-dotenv 0.19.2; most of the rest come from jupyterlab/jupyter-server/ipykernel, declared as runtime dependencies though no code imports them). The configuration is unsafe by default: with no `SECRET_KEY` the app silently generates a weak, per-process lowercase key; `apps/config.py` and `run.py` `print` the DB variables and `DEBUG`; and in debug mode `run.py` logs the full SQLAlchemy URI, database password included. There is no CI, no test, and the open-source alignment left residue: no `Language:` line in AGENTS.md, no `CITATION.cff`, and no documentation site because `requires-python ==3.10.12` and the unpinned `seleniumbase` kept `zensical` from resolving.

## Proposal

Bring every direct dependency to a release without known vulnerabilities (Flask 3.1.x line and its stack), drop the runtime dependencies nothing imports, move notebook tooling out of runtime, and refactor the code Flask 3 no longer supports (`before_first_request`). Fail fast on a missing `SECRET_KEY` outside debug, replace the `print` calls with logging and never log credentials. Add a smoke test suite and a GitHub Actions CI (tests, dependency audit, secret scan). Close the alignment residue: `Language:` line, `CITATION.cff`, the documentation site build.

## Out of Scope

- The known limitations SECURITY.md already documents (plain-text Keychain credentials, open `/register`, string-formatted internal queries) — each is its own behavior change.
- `.github/FUNDING.yml`: needs a funding account the owner has not declared.
- Upgrading the vendored AdminLTE front-end plugins.

## Design

- Dependencies: `pyproject.toml` is the single source; `requires-python = ">=3.10,<3.13"`; `.python-version` stays on 3.10. Remove `flask-restx`, `thefuzz`, `unidecode`, `webdriver_manager`, `seleniumbase`, `email_validator` only if unused, `ipykernel`, `jupyterlab` from runtime (grep proves none is imported by `apps/`, `projetos/` or `run.py`); add `requests` explicitly (imported by the example project); `pytest`, `zensical` go to a `dev` dependency group. `requirements.txt` is regenerated from the lock with `uv export` so pip users keep a path.
- Flask 3: replace `@app.before_first_request` with `db.create_all()` inside `app.app_context()` in `create_app`, keeping the SQLite fallback on a DBMS error.
- `SECRET_KEY`: in `ProductionConfig` a missing key raises at startup with a message pointing to `.env.example`; `DebugConfig` may generate one with `secrets.token_hex(32)` and logs a warning.
- Logging: `print` → `logging.getLogger(__name__)`; the DBMS line logs the URI with the password masked (`sqlalchemy.engine.make_url(...).render_as_string(hide_password=True)`).
- CI (`.github/workflows/ci.yml`): on push and pull request to `main`, Python 3.10 via `astral-sh/setup-uv`, `uv sync --frozen`, `uv run pytest`, `uvx pip-audit` against `uv export --frozen`, gitleaks over the history. Actions pinned to a full commit SHA; `permissions: contents: read`.

## Alternatives Considered

- Pin each vulnerable package to its minimal patched version on the Flask 2.x line — rejected: Flask 2.x and Werkzeug 2.x no longer receive fixes, so the advisories would reopen.
- Keep notebook tooling (`jupyterlab`, `ipykernel`) as runtime dependencies — rejected: nothing imports them and they carry most of the audited vulnerabilities; a contributor who wants notebooks installs them locally.
- Keep generating a random `SECRET_KEY` in production — rejected: sessions silently break across workers and restarts and the default hides a misconfiguration.

## Open Decisions

- none — every decision is settled by the Design and the owner's declared autonomy ("siga de forma autônoma com todas as recomendações")

## Risks

- Flask/Werkzeug 3 may break a template or route behavior the smoke tests do not cover; the automation flow needs PostgreSQL and Selenium and is not exercised in CI.
- A user automation project outside this repository may rely on a removed dependency; the release note must name the removed packages.

**What shipped**

- Dependencies moved to vulnerability-free releases on the Flask 3.1 line and relocked (`uv.lock`, exported `requirements.txt`); `pip-audit` reports no known vulnerability.
- Runtime dependencies removed because nothing in `apps/`, `projetos/` or `run.py` imports them: `flask-restx`, `thefuzz`, `unidecode`, `webdriver_manager`, `seleniumbase`, `ipykernel`, `jupyterlab`. `pytest` and `zensical` live in the `dev` group.
- `before_first_request` (removed in Flask 3) replaced by an app-context `create_all`; the SQLite fallback now probes the DBMS before the engine is bound.
- `SECRET_KEY` is now required in production: `run.py` exits with a clear message when it is missing and `DEBUG=False`; under `DEBUG=True` a random per-process key is used with a warning.
- `print` replaced by `logging`; the logged database URI masks the password.
- A pytest smoke suite (7 tests) and a CI workflow (`test`, `audit`, `secrets` jobs, actions pinned by sha).
- `Language: pt-BR` in `AGENTS.md`, `CITATION.cff`, and a zensical documentation site (`zensical.toml`, `docs/project/documentation-site.md`).

**Left out / follow-ups**

- `zensical build` exits 0 with 5 warnings for repo-root-absolute `/docs/...` links (e.g. `docs/how-to/create-project.md:25`, `docs/standards/AGENTS.md:12`) that resolve on GitHub but not in the site; convert them to relative links.
- README's `uv run flask run` relies on Flask app discovery that does not find `run.py`; verify and document the right entry point.

**For the next reader**

Deployments must set `SECRET_KEY` before upgrading, or the app refuses to start in production. An automation project that needs one of the removed packages must declare it itself.
